# Build Accessibility Copilot - Hackathon MVP

You are building **Accessibility Copilot**, an AI-powered website accessibility auditing and remediation platform.

**Team:** Primordial  
**Hackathon:** CoNSTruct 2.0  
**Target standard:** WCAG 2.1 Level AA

## 1. Main Objective

Build a working, polished MVP that allows a developer to:

1. Enter a publicly accessible website URL.
2. Scan the website for accessibility problems.
3. View detected violations and their severity.
4. Identify the exact elements causing violations using visual highlights.
5. Generate AI-assisted code fixes.
6. Simulate applying fixes and verify them with another accessibility scan where technically supported.
7. Complete a human-review checklist.
8. Copy suggested code fixes.

This must be a functional application, not just a static UI prototype.

## 2. Technology Stack

Use:

- Frontend: Next.js with TypeScript.
- Styling: Tailwind CSS.
- Backend: Node.js and Express.js.
- Browser automation: Playwright with Chromium.
- Accessibility engine: Axe-core.
- AI remediation: Google Gemini API, called only when the user requests a fix.
- Validation: Zod.
- Database: MongoDB only for scan history if a MongoDB connection is configured. The application must still work without MongoDB.

Keep the project structure clean and modular.

## 3. Design Requirements

Create a modern developer-focused SaaS dashboard.

Visual direction:

- Professional, minimal, premium developer-tool appearance.
- Light background with dark navy text.
- Indigo or violet as the primary accent.
- White cards with subtle borders and restrained shadows.
- Clean typography and consistent spacing.
- Rounded corners, but avoid excessive decoration.
- Responsive layout for desktop and mobile.
- Clear visual hierarchy.
- No unnecessary gradients, animations, or decorative illustrations.

The interface must look like a real accessibility engineering product, not a generic AI chatbot.

## 4. Main Screens

### A. Landing / Dashboard

Include:

- Product name: Accessibility Copilot.
- Short description: "Find accessibility issues. Understand them. Fix them."
- URL input field.
- Scan Website button.
- Short explanation of the scanning process.
- Recent scan history if MongoDB is configured.

### B. Scan Loading State

Show clear progress stages:

1. Validating URL.
2. Launching browser.
3. Loading website.
4. Running accessibility checks.
5. Preparing results.

Display useful error messages if a scan fails.

### C. Results Dashboard

Show:

- Total violations.
- Critical/serious violations.
- Moderate/minor violations.
- Accessibility health indicator.
- Website screenshot or visual preview.
- Violation list.
- Filters by severity and WCAG principle.

Do not present the health indicator as an official WCAG compliance score. Label it as an internal estimated accessibility indicator.

### D. Visual Issue Locator

For each violation:

- Show its issue name.
- Show severity.
- Show affected HTML element.
- Show the Axe-core description.
- Show the relevant WCAG reference.
- Show the element's location on the captured screenshot when coordinates are available.

Use color-coded bounding boxes:

- Red: Critical.
- Orange: Serious.
- Yellow: Moderate.
- Blue: Minor.

Clicking an issue should highlight its corresponding location.

If screenshot coordinates cannot be reliably mapped, show the issue details without inventing a location.

### E. AI Remediation Panel

Each issue card should have a "Generate AI Fix" button.

When clicked:

- Send only the selected violation's relevant context to the backend.
- Ask Gemini to generate a suggested code correction.
- Display the original code and suggested code.
- Explain why the original code causes an accessibility problem.
- Explain the suggested correction.
- Include the applicable WCAG reference.
- Provide a Copy Fix button.

Use structured JSON output and validate the response.

Do not automatically call the AI for every violation. Only call it when the user clicks the button.

If GEMINI_API_KEY is unavailable, display a clear configuration message and provide deterministic suggestions for supported common issues where possible.

### F. Apply and Verify

Provide an "Apply & Verify" button for generated fixes.

For the MVP:

- Apply the suggested patch to an isolated in-memory test representation.
- Re-run Axe-core where the testing environment supports it.
- Compare the original and resulting violation.
- Show one of these statuses:
  - Verified in simulation.
  - Issue still detected.
  - Regression detected.
  - Verification unavailable.

Clearly distinguish simulated verification from testing the actual production website or modifying its source repository.

Never claim a fix is verified if no successful re-test occurred.

### G. Human Review Checklist

Create a separate checklist for accessibility requirements that cannot be reliably judged by automated scanning.

Include examples:

- Does the image's alternative text accurately describe its purpose?
- Is the page usable with keyboard navigation?
- Is the focus order logical?
- Are headings structured meaningfully?
- Are important visual elements understandable without relying only on color?

Allow users to mark items as Reviewed, Needs Attention, or Not Applicable.

### H. Export

Allow users to:

- Copy suggested code.
- Copy issue descriptions.
- Copy a concise scan summary.

## 5. Backend and Scanning Requirements

Create Express API endpoints:

- POST /api/scan
- GET /api/scan/:id
- POST /api/remediate
- POST /api/verify

For scanning:

1. Validate the submitted URL.
2. Accept only HTTP and HTTPS URLs.
3. Reject localhost, loopback, private IP ranges, link-local addresses, and cloud metadata addresses.
4. Resolve and validate DNS destinations to reduce SSRF and DNS-rebinding risks.
5. Launch Playwright Chromium with a fixed viewport.
6. Navigate with a strict timeout.
7. Inject Axe-core.
8. Run WCAG 2.0 and 2.1 Level A and AA rules.
9. Extract violations, descriptions, impact, help links, affected HTML, selectors and available bounding-box coordinates.
10. Capture a screenshot.
11. Return normalized JSON results.

Handle browser launch failures, blocked websites, invalid URLs, timeouts and empty scan results safely.

Never expose server credentials or API keys to the browser.

## 6. AI and Cost Controls

- AI must only run after an explicit user action.
- Do not send screenshots to the AI by default.
- Send only the minimum required DOM and accessibility information.
- Keep AI output structured.
- Do not automatically retry failed AI requests.
- Do not make background AI calls.
- Do not add an AI chatbot.
- Use Gemini API through a backend environment variable named GEMINI_API_KEY.
- Keep the model name configurable through GEMINI_MODEL.

## 7. Scope Restrictions

Do NOT build these features in this MVP:

- User authentication.
- Subscription or payment systems.
- GitHub OAuth or automated pull requests.
- Full-site crawling.
- Multiple-page scanning.
- VS Code extensions.
- PDF/EPUB scanning.
- Enterprise administration.
- Complex analytics.
- Real-time collaboration.

These are future roadmap features.

## 8. Engineering Requirements

- Use reusable frontend components.
- Keep backend routes, services and validation separate.
- Use TypeScript.
- Add loading, empty, success and error states.
- Validate all API inputs.
- Handle errors without crashing the application.
- Keep secrets in Replit Secrets.
- Never hardcode API keys.
- Keep dependencies minimal.
- Do not install unnecessary packages.
- Do not create duplicate files or unnecessary abstractions.

## 9. Development Instructions

Build this in small, controlled stages.

First create the complete application structure and the main dashboard.

Then implement the real URL scanning pipeline using Playwright and Axe-core.

Then implement issue visualization, AI remediation, verification simulation and the human-review checklist.

Prioritize a working end-to-end flow over extra features.

Before adding a dependency, check whether the existing project already has a suitable package.

Do not rewrite working code unnecessarily.

Do not claim a feature is implemented unless it actually works.

Do not invent scan results, benchmark numbers, test results or accessibility improvements.

## 10. Definition of Done

The MVP is complete when:

1. The application starts successfully on Replit.
2. A user can submit a valid public website URL.
3. Playwright can load a supported website.
4. Axe-core can detect accessibility violations.
5. Results appear in a usable dashboard.
6. The user can inspect individual issues.
7. The user can request an AI-generated fix.
8. The user can copy the suggested code.
9. Verification reports an honest result.
10. The human-review checklist works.
11. The application handles invalid URLs and scan failures.
12. The interface is responsive and visually polished.

**Important:** Do not build beyond this scope. Focus on a stable, demonstrable hackathon MVP.
